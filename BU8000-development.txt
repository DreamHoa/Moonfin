2026-11-14: migrated the device-validated Litefin no-store policy to the same MKV subtitle Range fetch in Moonfin. Native video playback and the libpgs decoder are unchanged.
Removed the unbounded outer per-cue retry added in the previous customization. The existing three-attempt request budget and body timeout remain; a persistently unavailable cue may be skipped so later subtitles can continue.
Regression validation: two new tests failed before the fix; four related suites and 74 tests pass after it. Full build lint and production compilation passed.
Signed build 20261114.3-cache was installed in place, retained the session, and all 130 top-level JavaScript files matched the signed package. PGS canvas samples contained changing subtitle images during playback and after forward/backward seeks using Moonfin's own AVPlay seek wrapper.
Observed first pixels after seek initiation: +10 seconds 6.314s (seek callback 5.229s), +600 seconds 7.067s (callback 2.829s), -600 seconds 12.679s (callback 2.897s). These times include native seeking and dialogue gaps; they do not isolate subtitle fetch latency. This is bounded sample validation, not proof that all intermittent omissions are eliminated. Large backward seeks still have a visible wait.
The preceding baseline commit preserves the previously installed customization for comparison; its PGS device acceptance had failed. It is not a known-good subtitle baseline.

2026-11-14: remaining backward-seek delay investigation, candidate 20261114.4-progressive
A fixed backward seek to 183.549 seconds on the previous build completed natively at 3.096s, but its PGS timeline first covered playback at 8.842s (video position 190.941s). The subtitle should have appeared at 186.603-188.230s, so it was missed; the next composition at 194.236s explains the observed first pixels at 12.793s.
Port the existing Litefin delivery changes: validate and reuse the target composition, coalesce normal payloads in a bounded 32-KiB read, deliver ready compositions in timestamp order instead of waiting for the whole lookahead batch, and stop subsequent batches after disposal. Retain bounded retries and no-store.
Also port the already-decoded timeline publication in the adapter: libpgs progress notifications can be throttled when a fast batch finishes before one second, so the shared parsed timeline must be published before rendering. No decoder or timestamp alteration.
Five new regressions failed on the previous code; all 79 related tests pass on this candidate. Existing tests now consume through the same timestamps across progressive chunks, retaining ordering, seek, oversized-tail and bounded-retry checks. Device A/B validation pending.

Follow-up candidate 20261114.5-seek: the progressive build brought target data readiness from 8.842s to 4.855s in the first device run, but arbitrary nonzero pixels were rejected as an acceptance metric: the externally owned canvas retained pixels from the disposed renderer. libpgs owns neither this canvas nor its cleanup. Match Litefin's cleanup by clearing the canvas when disposing the in-band adapter.
A new regression failed before canvas cleanup; all 80 related tests pass afterward. Final device validation must identify the actual drawn PGS timestamp and verify clear compositions, excluding residual pixels. Build and final device acceptance pending.

The strict .5 run cleared residual pixels correctly, but still missed the short destination subtitle: data became available at 8.656s and valid pixels at 13.739s under approximately 0.5s request RTT. This run is explicitly not a seek-latency acceptance pass.
The remaining repeated work is identified in the request trace: every decoder recreation downloads the same file header and split cue index before requesting target data. Candidate 20261114.6-index reuses only that immutable parsed index through an explicit source cache scoped by a WeakMap to the existing playback track object. URL and subtitle ordinal must match; the target composition still uses fresh no-store reads and its own cursor. The cache is not global by URL and is not persisted.
A reuse regression fails on .5; all 83 related tests pass on .6, including fresh data reads, URL/ordinal isolation and object-lifetime scope. Final device validation pending.

2026-11-14 Stage decision: freeze further PGS patches. The scoped-index run removed repeated metadata requests, brought target timeline availability to 3.896s and valid pixels to 4.334s, and correctly cleared the canvas. However, a later 2.211-second composition was not drawn while the decoder reported index -1. Complete subtitle acceptance remains failed; the speedup is not evidence that all omissions are fixed. Investigate that fixed missing-composition case before any future subtitle redesign.
Current next stages: verify actual HDR playback, then profile global UI responsiveness. Runtime subtitle probes have been removed. No further production code changes are included in this stage record.

2026-11-15 review fixes, accepted build 20261115.9-clear:
Escape subtitle HTML and allow only limited formatting/colors. Keep physical subtitle tracks separate
from the render route, retain native fallback capability, and decline unsupported Web Streams runtimes.
For PGS, rebuild Normal-composition dependencies, avoid caching an unloaded next frame in libpgs 0.8.1,
and supply two lookahead sets (the stream parser peeks ahead and timestamp lookup also needs a later set).
Fetch imminent compositions alongside context. A blank target may skip older context only after the
following acquisition has been verified as independent; this avoids regressing short seek destinations.

Device comparison used the same episode and seek to 183.549 seconds. The old build missed the whole
202.911-205.122 composition. The accepted build drew it at 202.936, with all five observed dialogue sets
drawn in their valid intervals. The first short composition drew at 186.935 versus 186.886 on the old
build (49 ms difference; these are AVPlay clock observations with a 500 ms update loop, not panel latency).
A large forward/backward seek drew the first destination composition at 186.898. A valid constructed
Normal-composition fixture rendered 1542 nontransparent pixels on the TV using its preceding epoch.
The installed sanitizer no longer created or executed the isolated img/onerror test element.

An initial context candidate missed the first short line and was rejected. A later additional SRT
cache/progressive-delivery experiment passed unit tests but did not finish device acceptance: native
clock stalls and a seek-callback timeout were observed. That experiment was withdrawn; the accepted
source and package retain the original mkvTextSource. No claim is made that existing SRT cold-load
latency or all native buffering waits have been resolved. Native mapping/legacy capability fallbacks
have regression tests; unsupported TV track omissions are refused rather than guessed.

Acceptance is limited to the recorded fixtures and playback windows, not every file or firmware.
